These are conceptual attribute proposals, not final Malli schemas. New records need the standard owner and metadata fields. Validate relation targets against the source, metric capabilities, and ownership. Do not accept arbitrary query expressions from a saved collection.

The mockup fixes a 56-day goal period, with 28 complete days and 28 remaining. The product needs editable dates and cadence. A practice can have no goal or several goals with non-overlapping display contexts; the preview shows one goal per practice.

Existing schema relationships can supply pickers. Source capabilities determine which measures are offered. The builder demonstrates project and habit sources; the board also exercises meditation, reading, and exercise adapters.

Adding a new habit or project should cost data entry only. Adding a new entity type can require an adapter and capability declaration. That is the honest boundary of “generic.”

A daily series needs more than a number

{dates, values, unit, coverage, timezone, source-description}

The shared arithmetic takes this normalized result. The source adapters decide what a value means and whether it is known.

  • Zero and unknown differ. An unimported period cannot become a row of misses. Missing coverage hides affected comparisons.
  • Duration needs interval handling. Clip intervals to the window, split at timezone boundaries, and union overlaps within a collection.
  • Active days need set union. Two selected projects on one day still produce one active day.
  • All-habit routines need set inclusion. Brush, floss, and skincare can come from several logs on the same day.
  • Scopes must remain explicit. A source picker is not permission to read another user’s records.
  • Metric capabilities constrain charts. Only additive, nonnegative quantities get cumulative totals and remaining-pace math.

The fake records use pre-bucketed dates and non-overlapping closed durations. This isolates the dashboard behavior; it does not verify production timezone, overlap, query, or authorization logic.

What I would not copy uncritically

A rate ratio is comparable, not a priority score.

Twice your usual flossing rate may be impossible once you floss daily. Twice your reading minutes means something different.

The table shows the ratio without ranking your values. Active-day goals exceeding the available days get an explicit infeasibility message.

A page position is not pages read.

Subtracting consecutive end positions silently miscounts skipped logs, rereads, and jumps. Keep remaining-in-book separate from cumulative reading volume.

A current position plus an edition’s length still earns its capture cost for “18 pages left.” It does not belong in the generic sum adapter.

More output is not always better work.

Editing can remove words. A software session can remove code. Time goals remain valid when the purpose is protecting attention.

Add output fields only for practices with a deliberately chosen additive unit. Missing output remains unknown, not zero.

Groups do not have to become new entities immediately.

A user can save a set of project IDs today. Winddown can be one habit or an all-habits collection.

Add project tags when maintaining explicit selections becomes tedious. Add routine schedules when midnight boundaries and expected days need them.

How scope changes should behave

For an explicit ID collection, new projects do not appear until selected. Renaming a project does not change membership.

For future tag-based collections, membership can change automatically. Show that policy before saving; it can recalculate history.

Treat definitions attached to active goals as versioned. A scope edit should explicitly choose “recalculate this goal” or “use this definition for future goals.” Silently changing past goal progress undermines trust.

Implementation direction, if this earns a build

Start with a saved collection, a fixed-period goal, and project/habit adapters. Build the pace board on top.

That proves reuse across arbitrary user projects and habits without adding categories, output fields, reading fields, or activity-specific screens first.

The existing viz routes identify temporal patterns. Extend the idea with explicit metric capabilities and relationship scopes. Keep domain reads inside db/queries.clj, with targeted user/window scans and page pulls. Broad project history should not be pulled just to filter one collection.

Use ECharts for cumulative lines, required-rate history, and period comparisons. Use a Cartesian heatmap for aligned practice rows; ECharts does not require calendar coordinates. The exploration uses inline SVG and HTML to remain independently openable offline.

Try these before judging the abstraction

  1. Switch between both fictional users. The labels and source collections change; the layout and calculations do not.
  2. Select Winddown. Its daily value requires all three habits, even when recorded separately.
  3. Create “Anything I want” using two projects and active days. Compare it with the same scope measured in minutes.
  4. Switch your new practice between all three views. Inspect the daily values at the bottom.
  5. Create a habit collection with one habit, then several using “all.” The new collection should reflect the stricter definition.
