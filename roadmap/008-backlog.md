**Issues:**

### Observed issues (2026-09-19)

Two concrete defects behind the redesign, both verified in the code:

- ~~**Table view can't scroll horizontally.**~~ — FIXED 2026-09-21.
  `.table-container` applied `overflow-hidden`, so columns past the viewport
  were clipped with no way to reach them. Now `overflow-x-auto
  overflow-y-hidden` (`resources/tailwind.css`) — the rounded corners still
  clip vertically. Also fixes the medication-history and habit-log tables,
  which share the class.
  - **Measured, 390px viewport, `/app/crud/habit?view=table`:** the table was
    already 671px against a 322px container *before* the change — it overflowed
    fine, `overflow: hidden` just refused to scroll it. Edit/Delete and the
    Notes and Sensitive columns were unreachable; they now scroll into view
    (scrollLeft 0 → 349). Before/after pair in `e2e/screenshots/`
    (`before-table-scroll-mobile.png`, `after-table-scroll-mobile-scrolled.png`).
  - **The per-column `max-width: 250px` was left alone.** Changing it to a
    fixed `width` was tried and reverted: the measurement above shows it was
    never what caused the clipping, and making columns a hard 250px would push
    wide tables into horizontal scrolling on *desktop* too — a layout decision
    that belongs with the CRUD redesign, not a clipping bugfix.
- **Edit / delete actions look incohesive across the three list views.** Table
  rows get two text links (`views.clj:167-181`); list rows get the same two
  links in a hover-revealed column (`views.clj:717-728`); card view puts a
  delete form absolutely positioned at the bottom-right with edit only as the
  whole-card link (`views.clj:528+`). Three different affordances for the same
  pair of actions. Pick one treatment (icon buttons, consistent placement,
  consistent visibility rules) and apply it to all three.

### ~~Home Timeline Renders Over Mobile Top Bar (z-index)~~ — FIXED 2026-07-28
User-reported with screenshots (2026-07-27): on mobile, scrolling the home
overview timeline puts the entry icons and the sticky day headings ("Today",
"Yesterday") on top of the fixed hamburger/wordmark bar.
- **Confirmed cause**: the fixed mobile bar (`app/shared.clj` `#menu-btn`) had
  no z-index (`z-index: auto`) while the timeline's day headers (`z-20`) and
  icon circles (`z-10`) painted above it.
- **Fix**: `#menu-btn` gains `z-40` — above page content, below the `z-50`
  sidebar it toggles. Its `bg-dark-surface` (`#161b22`) was already opaque.
- **Verified**: computed style on a 390×844 viewport is `z-index: 40 /
  fixed`; mid-scroll screenshot shows timeline content passing cleanly
  underneath. The desktop calendar's own fixed bar also uses `z-40` but is
  `md:block`-only, so the two never coexist.

### ~~Timeline Day Headings Never Stick~~ — RESOLVED 2026-07-28 by removing the feature

The home timeline's day headings carried `position: sticky` and had **never
pinned**, on any viewport, since they were written.

**Root cause (corrected).** Not the app shell, as first diagnosed.
`resources/tailwind.css` sets `overflow-x: hidden` on both `html` and `body` —
a deliberate iOS Safari fix, documented there, stopping html/body expanding
past the viewport when a descendant is wider than the screen. Per spec a
non-`visible` overflow on one axis forces the other to compute to `auto`, so
`body` becomes a scroll container. `position: sticky` then resolves against
`body`, which never scrolls internally (the viewport does), so nothing pins.

The app shell's own `overflow-x-hidden` (`app/shared.clj`) is a second,
nearer instance of the same thing. Removing it alone would have fixed nothing.

**Resolution.** The owner decided a pinned day heading isn't wanted on that
page, so the sticky classes were removed rather than the iOS fix reworked.
Zero visual change — nothing was ever pinning. This also retires the risky
option of unpicking the html/body overflow rule.

**Consequence worth knowing: `position: sticky` does not work anywhere in this
app.** Any future sticky element will be silently inert. If one is ever
genuinely needed, the iOS overflow fix has to be reworked first — probably by
scoping the horizontal clamp to the specific wide descendants instead of
html/body.

### ~~Landing page header is sticky but inert~~ — RESOLVED 2026-09-21

`home.clj` marked the landing page header `sticky top-0 z-10`. It was dead for
the same global reason as above (verified: its viewport top traced
0 → -150 → -300 while scrolling past it, rather than clamping at 0).

**Resolution.** Dropped as dead code, with a comment at the call site pointing
at the iOS overflow fix. Zero visual change — nothing was pinning. If a pinned
marketing header is ever actually wanted, the html/body `overflow-x: hidden`
rule has to be reworked first (scoping the horizontal clamp to the specific
wide descendants). The one *working* sticky in the app is the goals table
`thead`, which sits inside its own `overflow-auto` scroll container
(`app/goals.clj`) rather than resolving against `body`.

### ~~Canceled Tasks Highlighted as Actionable on Home Timeline~~ — FIXED 2026-09-21
Canceled tasks on the home timeline got the amber "actionable" highlight (ring,
icon, badge) when their due date was today or earlier, even though they're no
longer actionable.
- **Cause**: `entity-status` in `src/tech/jgood/gleanmo/app/overview.clj`
  marked a task `:actionable` when `:task/state` was `:now` or when
  `:task/due-on` / `:task/focus-date` was today-or-earlier — with no check for
  terminal states.
- **Fix**: `entity-status` now guards the `:actionable` branch with
  `(not (terminal-task-states (:task/state entity)))`, covering `:done` as well
  as `:canceled`. The set is declared locally in `overview.clj` rather than
  reached for across namespaces (`task_focus.clj` has its own private copy).
  Covered by `entity-status-test` in
  `test/tech/jgood/gleanmo/test/app/overview_test.clj`.

### ~~Home Page Active Timers Don't Tick~~ — FIXED 2026-09-21
The "Running now" cards on the home overview showed a frozen elapsed time —
whatever it was when the fragment was rendered.
- **Cause**: `active-timer-summaries` computed `(elapsed-duration start)`
  server-side and `render-active-timers` printed that string. Nothing carried
  the start timestamp to the client.
- **Fix**: the elapsed cell now carries `data-epoch-ms` / `data-fmt "session"`
  and the client formats it every second, the same mechanism the workout and
  bouldering screens use. The server-side `elapsed-duration` helper and the
  `:elapsed` key on the summary map are gone. The `[:script]` lives inside
  `render-active-timers`, so it runs when htmx swaps the fragment in.
- **Also**: the tick script and `epoch-ms` had been copy-pasted into both
  `app/workout.clj` and `app/boulder.clj`; adding a third copy was the wrong
  move, so both now alias `shared/tick-script` and `shared/epoch-ms` from
  `app/shared.clj`. The shared `"session"` format gained a sub-minute case
  (`45s` instead of `0 min`), which also fixes a just-started workout or
  bouldering session reading `0 min` for its first minute.
- **Related**: `066-unified-timer-page.md` for the timer workspace, and
  `088-timer-cross-device-staleness.md` for the adjacent problem this brought
  into focus — nothing invalidates the tick, so a timer stopped on another
  device keeps counting up on the home page indefinitely.

## Testing

### `test:goals` flakes on a seconds-precision datetime fill
Observed once in `just e2e-test-all` on 2026-09-21, at step 8 ("Counting today
while pace uses completed days"). Unrelated to the change being tested, and it
passed three consecutive runs in isolation plus two further full-suite runs.
- **Error**: `locator.fill: Error: Malformed value`, filling
  `input[name="reading-log/beginning"]` with `"2026-09-21T17:30:00"` against a
  `datetime-local` input whose own value was minute-precision
  (`2026-09-21T17:31`) and which carries no `step` attribute.
- **Source**: `e2e/scripts/test-goals.ts:352-365` deliberately builds
  seconds-precision strings (`.toISOString().slice(0, 19)`) with the comment
  "Use seconds so this remains valid even during the first minute of a UTC
  day." A `datetime-local` without `step` only accepts `YYYY-MM-DDTHH:MM`, so
  that workaround is fighting the input.
- **Likely fix**: give the input a `step` that permits seconds, or keep the
  test at minute precision and solve the first-minute-of-day edge another way
  (e.g. skip that assertion, or pin the clock).
- Worth confirming the trigger before changing anything — the intermittency is
  not yet explained, and a test that fails ~1 run in 5 is worse than one that
  fails every time.
